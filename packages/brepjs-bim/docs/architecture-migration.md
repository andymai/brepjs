## Acceptance scenarios

The central criterion in [ADR-0001](adr/0001-independent-product-representation-and-placement.md) is that adding a class of physical element using an existing representation requires no changes to shared geometry ownership, disposal, Placement, or aggregate measurement. Review the extension diff as well as its runtime results.

Legitimate class-specific changes remain: classification and payload/role validation, legal representation/relationship combinations, optional convenience authoring commands, shape-generating recipes, opening/filling restrictions, IFC entity/schema/predefined-type and reusable-type mappings, applicable quantities/property sets, standards-specific projections, documentation, and focused tests. Registering an IFC class in a complete semantic handler map is expected. Re-registering it in geometry lifecycle lists is a failed architecture probe.

### Step-2 extension check

At the end of step 2, implement repository-owned IfcSign and direct IfcMember probes against the new interfaces. The earlier IfcSign external experiment motivates the case; its branch and diff are not implementation dependencies or acceptance evidence. For each classification, retain singleton and multi-item Bodies, exercise shared transforms and measurement, and verify cleanup. Inspect each extension diff. No class registration may be added to shared geometry ownership, `placedGeometry` or its replacement, disposal, or aggregate measurement. Class-specific semantic mappings, authoring validation, and focused tests remain legitimate changes.

The step-2 check measures extension cost and Body behavior before the document cutover. Full document-owned parent-chain resolution follows in step 3; end-to-end IFC and semantic checks follow in step 4 after review of the Deferred ADRs. Preserve existing export/import regressions at every step. The maintainer [confirmed this division of acceptance in the step-0 review](https://github.com/andymai/brepjs/pull/2313#issuecomment-5670327868).

| Scenario                                | Required observable outcome                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Frame queries with and without geometry | Use the same operation for a physical element, spatial container, and `NONE` assembly under translated and rotated ancestors. Own-local returns identity; World composes the full chain; a named target in another branch returns `inverse(WorldTargetFrame) × WorldSourceFrame`. Results identify both frames. No query realizes or allocates geometry. ### IFC semantic preservation and qualification

These step-4 review drafts cover [ADR-0006](adr/0006-ifc-exchange-adapter.md), [ADR-0007](adr/0007-ifc-import-fidelity-and-item-outcomes.md), and [ADR-0008](adr/0008-explicit-bim-type-identity.md). The acceptance path is authored document → IFC → imported-document read contract for the declared supported subset. It does not require arbitrary source IFC re-export, imported-to-authored normalization, or recovery of editable Family generators. An independent reader must verify the emitted semantic graph as well as the public import result. Entity counts and effective property values alone cannot prove retention.

| Scenario                                                                | Required observable outcome                                                                                                                                                                                                                                                                  |
| ----------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| One Family definition, 100 physical elements, two explicit BIM types    | Preserve all stable physical element identities, exactly two explicit type identities, and every membership. Shared properties and occurrence overrides remain separately inspectable after export and import.                                                                               |
| Different type keys with identical geometry                             | Both definitions and their memberships survive. Changing geometry alone does not merge or redefine types. Conflicting reuse of a definition key fails before mutation.                                                                                                                       |
| Untyped physical elements                                               | Export remains untyped where the profile permits. A profile requiring types rejects missing definitions unless an explicit supported synthetic policy is selected. Any synthetic grouping is reported and never merges authored or imported types.                                           |
| Multiple external classifications on types and elements                 | Preserve every supported association, its scope, supplied system/reference URIs and parent chain. References using the same system name and code in different editions remain distinct. Missing optional fields remain absent; an IDS requirement can make their absence a delivery failure. |
| Invalid enums, incompatible class/type pairs, and illegal relationships | Document commands reject illegal neutral graphs atomically. Required export checks reject unsupported mappings. Independently validate deliberately malformed IFC fixtures to prove the external checks detect violations that permissive parsing can miss.                                  |
| Placement parenting differs from containment and decomposition          | Preserve each relationship independently and retain the expected World frames. Aggregation and ordered nesting remain distinguishable; serialization does not drop invalid endpoints or invent placement edges.                                                                              |
| Failed geometry with retained semantic data                             | Source identity, supported type membership, property scopes, classifications, and relationships remain inspectable. Geometry failure does not erase semantics; unsupported semantic data has explicit outcomes and is not counted as preserved.                                              |
| Missing validation or unchanged counts despite changed meaning          | Changing a classification, type membership, or property must fail semantic comparison even if entity counts match. Failed, unavailable, or unrun required checks prevent qualification. A successful internal re-open cannot override that result.                                           |

After step-4 review accepts the qualification scope, CI generates new bytes from the candidate implementation for each claimed schema/profile and runs independent STEP syntax, EXPRESS, applicable normative rules, project IDS requirements, semantic comparisons, and geometry checks. Assert the expected subject coverage so an empty model or zero reconstructed products cannot pass accidentally. Keep geometry tolerances and all-item checks from the existing scenarios. Use the [proposed exchange qualification procedure](exchange-qualification.md) for the acceptance matrix and receipt. [VALIDATION.md](../VALIDATION.md) retains the existing upstream validation record and tool instructions.

## Migration order

Each numbered step is one PR against `andymai/brepjs`. Step 0 is documentation under `packages/brepjs-bim/docs/adr/` with the glossary and migration/validation notes. Each implementation step ships a breaking 0.x commit, using `feat(bim)!:` or `refactor(bim)!:`; the planned release-please flow cuts a minor release. Step 0 does not claim a runtime release. Do not retain compatibility aliases or a permanent facade.

Before implementation, identify the current upstream source commit and preserve its public regression tests. Keep existing IDS conformance in CI and local IfcOpenShell checks running throughout the migration. The temporary internal Families adapter described in ADR-0004 fails on unexpected structures, preserves #2270 regressions, and is removed in step 5; it does not keep retired public APIs alive.

0. **Documentation revision.** Submit this revised ADR series, glossary, and migration/validation notes against a fresh upstream baseline. Keep ADR-0001 through ADR-0004 Proposed for review and ADR-0005 through ADR-0008 Deferred. Check Markdown formatting, local links/anchors, source references, and agreement between representation terminology and acceptance stages. Call out the step-2 acceptance interpretation above in the PR description. This step changes no runtime source.
1. **Neutral placement and Body foundation.** Extend the existing `ProductBody`, `bodySolids()`, and `disposeProductBody()` with their #2286/#2295 tests. Change `EXACT` to `AUTHORITATIVE` and give `PARAMETRIC` a nonempty item collection. Move frame validation/algebra below adapters; implement transactional adoption and occupied-union measurement. Gate on singleton, disconnected, overlapping, invalid/aliased, and later-item failure cases, plus the analytical coincidence regression. Keep the `ProductBody` name until step 2. Do not implement grid/alignment solvers. Related decisions: ADR-0002, ADR-0003, ADR-0004.
2. **Representation convergence and extension check.** Move every stored-solid class onto Body ownership, including Roof, Proxy, and Earthworks Fill, and rename `ProductBody` to `Body`. Dispatch over `BODY | NONE`; authoring realizes flights into multi-item Bodies, while curtain-wall assemblies use `NONE` with separately placed Plate/Member children. Gate on exhaustive dispatch, consistent bounds/material measurement, and the absence of class lists in shared ownership, transform, and disposal operations. Implement the repository-owned Sign and direct Member probes against these interfaces, then pass the step-2 extension check before step 3 begins. Related decisions: ADR-0001, ADR-0002, ADR-0003.
3. **Document and authoring cutover.** Move recipe generation out of the document; provide direct authored-Body creation and document-owned parent-chain resolution. Preserve existing identity, metadata, type references, appearances, and relationships through replacement without requiring the deferred new type model. Gate on a shaped typed Roof, nested rotated World geometry, bodyless frame queries, moves, explicit `KEEP_LOCAL`/`KEEP_WORLD`, deletion dependencies, and atomic rejection. Retire `placedGeometry(element, parentFrame?)` and replace the existing model once. Related decisions: ADR-0001, ADR-0002, ADR-0004.
4. **Semantic and IFC convergence.** Re-review ADR-0006, ADR-0007, and ADR-0008 before implementation. Within the agreed scope, separate semantic handlers from Body/Placement encoding and complete item outcomes, type identity, property/classification scopes, appearance, and diagnostics. Preserve #2273/#2278 reconstruction and cleanup. Run Sign/Member exchange checks alongside the schema/profile matrix, negative semantic cases, partial/fatal failures, and thin-panel reload. Qualify fresh output independently; existing fixture passes do not qualify the new implementation. Record explicit Building/Bridge/Road/Railway support states, with Bridge first and unsupported authoring still out of scope.
5. **Typed Families cutover.** Re-review ADR-0005, then coordinate the target-independent Families contract, create-brepjs template, playground examples, and adapter changes. Delete display-name routing, whole-tree civil switching, wrapper recovery, and the temporary internal adapter. Gate on direct authored Roof preservation, #2259/#2270 regressions, explicit unsupported intent, bodyless assemblies, and no duplicate physical elements from helper nesting. Settle nested-Site legality separately before implementing that policy.
6. **Package entrypoints and release qualification.** Curate document/authoring/IFC/Families and focused standards entrypoints after the earlier extension probes have passed. Package-root model imports must not load IFC or Families transitively; remove the old barrel without compatibility re-exports. Gate on packed ESM/CJS/declaration consumers, dependency-direction checks, affected repository suites, and self-contained consumer fixtures. Independently qualify IFC bytes generated by those packed consumers and record results in each receiving application claimed by the release.

Geometry and cleanup checks run against supported native backends. For occt-wasm, read native arena counts through the raw kernel before and after completed ownership scopes, following [the upstream arena disposal tests](https://github.com/andymai/brepjs/blob/4602096ebc3c9ea0263d5b2a1b7d3b6dee24c466/tests/wasmArenaDisposal.test.ts#L1). JavaScript live-handle statistics alone cannot detect orphaned arena slots. Dispose probe-owned intermediates with `using` and test release calls separately. Step 0 runs documentation checks only and establishes no native geometry, exchange, or performance result.

## Non-goals and separate follow-up

- This documentation change does not implement the migration, update issue states, or authorize a release.
- No repository split, multiple BIM npm packages, full IFC-schema mirror, open runtime geometry registry, new writer backend, general constraint solver, or repository-wide owned/borrowed handle branding.
- Full grid/linear resolution, Road/Railway authoring, imported-to-authored normalization, per-item appearances, and configurable IFC units require separate scope. Preserve their intent/support states without claiming implementation.
- Additional schema aliases require a focused reader/capability check against upstream source and a repository-owned fixture. Alias recognition does not expand implemented exchange support. Configurable IFC output units remain a separate feature.
- Individual authoring, tessellation, and foreign-resource defects need reduced upstream reproductions and focused fixes. The architecture proposal does not establish those defects or justify replacing the writer backend.
- Exact nested-Site legality and root identity behavior require a focused hierarchy decision. Role-to-schema mapping needs its own review and must stay separate from physical element metadata and reusable type identity. The ADRs assign the owning modules without approving every proposed enum or hierarchy rule.
- Project-specific set-out, Family definition packaging, grading tools, and source-data corrections are outside this architecture migration.
- Optional versus mandatory `web-ifc` and Families dependency declarations remain deferred until packed consumers establish the release constraints. The focused entrypoint direction is retained; exact export names and peer packaging do not block the document/Body design.

## Engineering costs and risks

- Ownership and representation change before all adapters are replaced. Intermediate releases must preserve existing regressions and have a clear owner for every retained handle. A permanent second model would undermine the migration.
- Explicit authoring commands and direct Body adoption remove implicit conventions but break consumer integrations. Templates and examples need the same coordinated cutover as the adapter.
- Copies, recipe realization, preflight buffers, and occupied-union measurement add allocation and computation. Native failure handling and representative workloads must establish their cost; no performance gain is assumed.
- The deferred semantic and exchange work may expose further contract changes. Preserve existing metadata and relationships while those decisions remain open. A neutral document does not by itself expand IFC support.

## Evidence and maintenance

Implementation evidence cited by this architecture proposal comes only from `andymai/brepjs`. Existing upstream documents, including `VALIDATION.md`, retain their own references and are not rewritten to apply this proposal's citation policy. Earlier upstream commits and closed upstream PRs remain valid historical sources. Describe external work, including IfcSign, as an external experiment without quoting its code, measurements, or review as upstream evidence.

| Reference                                 | Use and maintenance                                                                                                                                                                                               |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Upstream file at a full commit SHA        | Evidence for behavior at that revision. Pin the file and relevant lines. Before implementation, compare the claim with the selected upstream base; keep or supersede the historical observation explicitly.       |
| Upstream issue, PR, or discussion         | Rationale and review history. Link the specific comment when relevant. Its body and status can change, so record the required conclusion in the ADR itself. A closed or merged PR is not proof of later behavior. |
| Branch, tag, comparison, or live PR diff  | A navigation aid only. Do not use it to substantiate fixed code behavior or change counts. Replace evidentiary links with a full upstream commit SHA.                                                             |
| Relative glossary, ADR, or migration link | The contract maintained with this checkout. Keep terminology in the glossary, rationale and status in the ADR, and scheduling in this note. Update affected documents together when the contract changes.         |

A commit fixes content, not permanent hosting availability. The decision must remain understandable without opening its links. Keep the limitation, chosen contract, and trade-off in the repository; use links for verification. Do not silently replace an old source SHA with a newer one without rechecking the associated claim. Record fresh test results against their exact source and artifacts, and label retained results as historical.
